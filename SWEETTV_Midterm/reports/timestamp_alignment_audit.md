# Timestamp Alignment Audit — Stage 2

Generated by `src/build_stage2_reports.py` from `reports/timestamp_semantics.json`.
All parsing is naive wall-clock arithmetic. **No timezone offset was applied**
to any timestamp, and no external timezone information was used or assumed.

## 1. What was tested

| Check | Method |
|---|---|
| Format parsing | Strict parser for `YYYY-MM-DD HH:MM:SS` (viewing) and `DD.MM.YYYY HH:MM:SS` (schedule) |
| Date ranges | Min/max over the full files |
| Interval comparison | Overlap of each sampled session against the same-channel schedule at each candidate offset |
| Boundary alignment | Distance from session start/end to the nearest programme start |
| Time-of-day | Minute-of-hour distributions of session starts vs programme starts |
| DST | The 117 duration discrepancies and the 2020-03-29 transition |
| Midnight / long sessions | Full-file counts and the duration tail |
| Durations | Viewing duration vs schedule programme duration |

Sample: every 50th viewing row
(116,439 sessions) for the offset sweep; all
5,821,987 rows for ranges, DST, midnight and long-session counts.

## 3. DST evidence

- Exactly **117** viewing rows have
  `duraton != stop_time - start_time`.
- Exactly **117** of them span
  `2020-03-29 03:00:00` — i.e. the set of duration
  mismatches and the set of sessions crossing the wall-clock jump are identical.
- All 117 differences are
  `-3600` seconds.
- The schedule itself skips the same hour: channel 3 has a gap from
  `2020-03-29 03:05:00` to `2020-03-29 04:05:00`, i.e. the wall clock jumped
  03:00 → 04:00 in both sources.

Interpretation: `duraton` is elapsed device time, while both timestamp columns
are **naive local wall-clock time with DST**. This is observed evidence, not an
assumption. It also means the join must not "fix" the 117 sessions with an
offset: their wall-clock interval is genuinely one hour longer than elapsed time.

| +10800 | 92.89% | 3.31% | 15.66% | 3.29% | 1198 s | 1209 s | 0.0513 |

Reading the table:

- **Coverage is flat** (92.83%–92.90%)
  at every offset. Schedule rows tile most of the broadcast day on most
  channels, so "any overlap" cannot identify the offset. This is why a weak
  coverage result must not be treated as proof.
- **Boundary alignment is not flat.** Offset 0 has the highest
  start-within-300 s (17.58% vs
  15.66%–17.58%),
  the highest end-within-60 s
  (4.81% vs
  3.18%–4.81%),
  and the smallest median distance to the nearest programme start and end.
- Absolute rates are low (≈18% of starts
  within 5 minutes of a programme boundary), because viewers usually tune in
  and out mid-programme. The signal is therefore **suggestive, not conclusive**.
- Offsets of ±1 h and ±3 h are consistently worse on every boundary metric,
  so a whole-hour clock mismatch is not supported.

Zero offset is the best of the tested alternatives on all three independent
boundary metrics; that is the strongest statement the data supports.

## 5. Does DST change the offset?

If the two sources handled DST differently, the best offset would move by
one hour after 2020-03-29.

| Window | Offset | Start within 60 s | End within 60 s |
|---|---:|---:|---:|
| before_2020-03-29T03:00 | -3600 | 3.46% | 3.58% |
| before_2020-03-29T03:00 | +0 | 3.76% | 4.98% |
| before_2020-03-29T03:00 | +3600 | 3.45% | 3.51% |
| after_2020-03-29T03:00 | -3600 | 3.52% | 3.41% |
| after_2020-03-29T03:00 | +0 | 3.69% | 4.76% |
| after_2020-03-29T03:00 | +3600 | 3.46% | 3.40% |

Offset 0 remains best before and after the transition. There is no evidence that
one source uses a different DST rule from the other.

Viewing sessions are much shorter than programmes: the median matched session

## 9. Conclusion and impact on matching

1. Both timestamp columns are naive **local wall-clock** strings; `duraton` is
   elapsed time. The DST jump explains all 117 discrepancies exactly.
2. Zero offset is the best-supported choice: best boundary alignment, smallest
   median boundary distance, and no DST-dependent shift. The margin is modest,
   so this is treated as **best available evidence, not proof**.
3. **No offset was applied** to any artifact. The interaction pipeline uses
   offset 0.
4. If the true offset were ±1 h, every session would shift by one hour. Counts
   would stay nearly identical (coverage is flat), but the matched programme
   identities would change. Because ±1 h is clearly worse on boundary metrics
   and because the schedule itself shows the local DST gap, a whole-hour error
   is unlikely. A sub-30-minute error cannot be excluded from these data.
5. The 117 DST-spanning sessions keep their wall-clock interval; their overlap
   with the schedule is one hour shorter than elapsed viewing because the
   broadcast wall clock skipped that hour. This affects
   117 of 5,821,987
   sessions (0.0020%).
